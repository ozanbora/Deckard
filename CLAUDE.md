# Deckard

Screen-recognition assistant for the Diablo games, in C# on .NET 10 for Windows 11. Current scope: Diablo 4, recognition only.

## Hard constraints

- Strictly external to the game: no memory reading, DLL injection, process hooks, or `OpenProcess` on game processes.
- D4, D2R and D3 get overlay and advisory features only. Never wire input automation to them, because Blizzard's terms forbid it and these games run Warden.
  Automation may exist only for offline classic D2 or private servers, as a separate module left out of the D4 build.
- Overlays must be our own topmost, layered, no-activate windows. Keep them click-through unless the user interacts with them on purpose (e.g. the draggable item card); never send input to the game. Never hook the game's DirectX `Present` call.
- Trading is listings only: prices in gold, never real money (Blizzard's terms forbid real-money trading). Players complete trades by hand in game; never automate whispers, the trade window or the stash.
- When a design choice raises anti-cheat or terms-of-service risk, call it out.

## Layout

- `src/Deckard.Core`: platform-neutral types (`Frame`, `IFrameSource`, `PixelCopy`) and `Items/` (`AffixCatalog`, `AffixTemplate`: loads `affix-templates.json` and matches OCR'd tooltip lines). Targets `net10.0`.
- `src/Deckard.Core/Builds`: `BuildPlanLoader` imports a link into a `BuildPlan` (variants, items per slot with affix ids, skill bar, skill points per step, paragon boards per step, how-to-play notes, mercenaries: hired with its tree picks, reinforcement with its skill and trigger, and the guide's mercenary notes): maxroll guide/planner links via `planners.maxroll.gg/profiles/d4/<id>`; d4builds.gg build pages (`D4BuildsImport`: the page's `page-data.json` names the build, read from the site's public Firestore REST API; names matched to catalog ids by `ImportNames`; no skill points, which d4builds stores in its own node order); Icy Veins planner links `icy-veins.com/d4/planner/?uid=<id>` (`IcyVeinsImport`, from `icy-veins.com/api/d4-builds/<id>/`: game keys and ids, skill points by index into the catalog's tree). Icy Veins guide pages sit behind a Cloudflare bot check: they are turned down with a pointer to the planner link, never worked around. `src/Deckard.Perception/Builds/BuildMatcher` scores a read item against the plan's item for its slot (a weapon or off-hand of a type the guide doesn't use, against the guide's weapons).
- Season data: the server serves each season's `affix-templates.json` and icons from its data root (`Trade:DataRoot`, else `data/d4`); the app gets both from the server. The tool that produces them is private and not in this repository: never add it, its sources or their processing here.
- `src/Deckard.Capture`: Windows.Graphics.Capture source (`WgcFrameSource`), D3D11 interop through Vortice, and `WindowLocator`.
- `src/Deckard.Perception`: Windows-only perception. `TooltipLocator` (finds tooltips by their bronze border, or a common item's grey-teal one, pixels only), `TextRecognizer` (Windows.Media.Ocr), `TooltipParser` (header, item power, affix lines matched via `AffixCatalog`), `TooltipReader` (ties them together), `ImageOps.PrepareForOcr` (brightest-channel grayscale, which reads colored values far better than the raw crop), `Zones/ZoneReader` (the zone name above the minimap, for location sharing; `deckard zone <image>` shows what it reads), and `Realms/RealmReader` (the picked character's realm under its name on the character select screen; when it differs from the Trade tab's, `TradeView.SetGameRealm` asks through a trade notice to switch). Misread values: `Tooltips/ReadCheck` flags a read value outside the range the tooltip prints after it, or far outside the season's roll range; `Tooltips/ReadCorrections` holds the player's corrections, keyed by what was read (per account in corrections.json; the feed applies them to each read, so build fit, stash verdict, price check and listings use the corrected values); `Deckard.App/ValueEditor` is the click-to-correct on the item card (which keeps the keyboard meanwhile, `OverlayVisibility.Hold`) and the Stash page, and `OverlayWindow.Caution` makes Queue and Sell show such values before a second click sends them. `Mercenaries/MercenaryPanel` reads the game's Mercenaries tab (the hired mercenary on its "Active:" line, the reinforcement or "NO REINFORCEMENT ENLISTED") and says what to change against the guide; the feed writes it under the tab's two boxes through the tree highlight overlay. On a mercenary's own panel (its Skills tab, named in the title) `MercenaryPanel.TreePicks` places the guide's picks on its skill tree, which doesn't pan or zoom (measured ratios), and the feed frames them, numbered in the order to take them.
- `src/Deckard.App`: WinUI 3 desktop app (unpackaged, self-contained). The app opens on `SignInWindow` and shows `MainWindow` only once the player is signed in (closing it unsigned quits; signing out from the title bar's account button returns to it), with Battle.net in the browser (the app listens on a loopback port for the server's one-time code) or, against a local server, development sign-in; the session is kept in Windows' Credential Locker, one per server address (a development server's token never reaches another), and the title bar's account button signs out. Each account's own settings (its builds in builds.json, most recent first, switched from the build header's Builds menu; quick searches; `AppSettings` in settings.json, whether it has seen the guide) live in `TradeClient.AccountFolder`, `%LOCALAPPDATA%\Deckardccounts\<user id>`; nothing about a build is kept outside it. `TrayIcon` puts Deckard in the notification area and registers the global Ctrl+Shift+D show/hide hotkey (both Win32 messages to the main window, which stays alive while hidden; closing it keeps Deckard in the tray unless `AppSettings.CloseToTray` is off). `StartWithWindows` writes the user's Run key; started that way (`--tray`) Deckard loads in the tray. The icon is drawn by `tools/icon/make_icon.py`. An account without a build gets a guided tour of the window (`MainWindow.ShowGuide`, TeachingTips) once; the title bar's help button replays it, then `GameData` downloads the season's `affix-templates.json` from the trade server into `%LOCALAPPDATA%\Deckard\data` (again only when its ETag changes) and `IconCache` the icons; `TradeClient.Shared` is the one connection, and `DECKARD_TRADE_SERVER` overrides the server address. `ItemFeed` runs capture and tooltip reading on a background thread; `OverlayWindow` (topmost, no-activate, shown while Alt is held over the game; Settings > Overlay can instead put the card in an ordinary Deckard window (taskbar, title bar, not topmost, always the last item read, never taking the focus when an item comes in) or not show it (`AppSettings.ItemCard`, `CardPlace`; `OverlayWindow.ApplyMode`; items are read either way), draggable and closable; with the pointer on it, it asks for the focus, which Windows usually refuses a background app, so a first click on it can still reach the game, which reads the mouse as raw input; the user chose to leave it so) shows the last item read as an `ItemCard` with its build fit and, for empty sockets, `Deckard.Perception/Builds/Runewords` advice (the guide's sockets for the slot, a guide runeword the player can make, else their own Ritual + Invocation pairs by Offering per cast; owned runes are learnt from rune tooltips, "TAL (4)", kept per account in runes.json, and runes first seen socketed in an item leave it (runes-socketed.json); `TooltipParser` puts what's socketed, runewords and gems' effects at the body's end, in `ItemTooltip.Socketed`, not among the affixes; runes' `ritual` and `offering` come from the season data); a hovered rune gets its own card (what it does, its Offering, the count, and "Saved to your Deckard runes" / "Updated" / "Couldn't tell which rune"), the rune told by its effect and Offering as well as its name (`Runewords.Identify`: OCR reads the font's Ø as C, 0 or another rune); `InventoryView` lays out the build's items, each named below its picture, with `PlannedItemTooltip` cards, and `BuildSheetView` beside it shows the runes, splinters and gems the build sockets (runes paired by the item they go in, then splinters and gems counted; hovering one shows what it does, from the season data's optional `lines` on goods and socketables; clicking a rune or gem searches the market for it, `TradeView.FindGoodsAsync`), the worn gear's progress and what's left to craft, the skill bar, the Warlock's soul shard and fragment (the planner's `warlockShard`/`warlockFragment`, named from the catalog's optional `classMechanics`; d4builds and Icy Veins imports have none) and the guide's how-to-play notes. The Mercenaries page (`MercenaryView`) shows the guide's mercenaries: the hired one's skill tree drawn by `SkillTreeView` (`FitWhole`) with the guide's picks lit and listed with what they do, the reinforcement with its skill and the player's skill that calls it, and the guide's mercenary notes (named and laid out from the season data's optional `mercenaries`, whose trees are laid out like the classes'; said plainly when the guide has none). The Talisman page (`TalismanView`) draws the seal and charms as the maxroll planner does: the seal in a round frame with the charms around it where the game puts each slot, then their names; a set charm's card lists its set's pieces, how many the build has and the bonuses that lights, counting a seal that lowers the charms needed (from the season data's optional `set`, `magicType` and `setDiscount` on items and `required` on set bonuses, with their fixed numbers filled in). Worn gear: `ItemFeed.EquippedRead` (tooltips with the EQUIPPED banner) → `Deckard.Perception/Builds/Gear` (`WornItem`, `Remember`, `Assign` to build slots, crafting `Tasks`), kept per account in worn.json, ticks in crafting-done.json; `MainWindow` is the build input and its tabs. The Stash tab (`StashView`) runs a sorting session: every item read is judged by `Deckard.Perception/Builds/StashSort` against each library build (keep / craft / sell with a price check / salvage). Patreon: Settings links the player's Patreon account in the browser (`TradeClient.LinkPatreonAsync`, the same loopback listener as Battle.net sign-in); `Supporter` keeps whether they're an active patron (the server's `GET /patreon`, asked after sign-in and on the Settings page) and the limits it lifts: saved quick searches (5, patrons 25), builds in the library (3, patrons any number; a full library says so instead of adding) and stash sorting (the shown build, patrons every library build). Patrons can show a name in the credits (Settings > Patreon; About lists `GET /supporters`), and on an early-access tier `Updater` takes the `early` channel from `/updates/early/` (`pack.ps1 -Channel early`). Only conveniences, checked in the app: nothing in the market depends on it (ROADMAP.md). `ErrorLog` writes what nothing caught (UI thread, background threads, unobserved tasks) to %LOCALAPPDATA%\Deckard\logs (a file a day, 7 days) and keeps the app running; `Deckard.Core/Diagnostics/Redaction` keeps only Deckard's own stack frames and hides the Windows user's folder. `Telemetry`: asked once at first start (and a switch in Settings > Privacy), kept for the Windows user in %LOCALAPPDATA%\Deckard	elemetry.json with a random install id that saying no forgets; counts and sizes only (pages, builds loaded, item cards, listings, tooltip lines matched per screen size, crashes as Deckard's own frames), batched to `POST /telemetry` every 5 minutes. `FeedbackWindow` (the title bar's Send feedback): a bug report or feature request with up to 3 screenshots (capture the game, capture Deckard, or a file); `Deckard.Perception/Feedback/ScreenshotRedaction` suggests black boxes (BattleTag-shaped OCR text, shared zones, the game's chat and party areas; the account button exactly), the player adds and removes them, and only the covered PNG goes to `POST /feedback`. Settings > Account: Download my data (`GET /account/export`, saved as JSON) and Delete my account (`DELETE /account` after a confirm dialog; then signs out, and by default deletes the account's folder on this PC). `SkillTreeView` and `ParagonView` (with leveling step pickers: green marks what a step adds, the in-game tree highlight follows the chosen step, choices kept per account in steps.json) draw the build's skill tree and paragon boards (from `AffixCatalog.SkillTrees` and `AffixCatalog.Paragon`) game-style. In-game paragon assistant: `Deckard.Perception/Paragon/ParagonLocator` finds the open paragon screen, full or docked in the Abilities panel (`ScreenLayout`, by which Paragon tab is lit), the grid's pitch and phase from the node symbols' light grey, and which cell is which by sliding the build's boards over the lit cells (a board counts as attached when most of its cells are lit); `ParagonGuide` turns the chosen paragon step into marks (the attached boards' build nodes, glyph sockets labelled with the glyph and level, the next board to attach outlined where it goes, turned as the build has it, with how to turn it) and the Paragon tab's checklist; `TreeHighlightOverlay` draws them like the skill tree's highlight. On the skill tree, `Deckard.Perception/SkillTrees/SkillRankReader` reads each build skill's in-game rank text ("4/15", OCR, kept once two reads agree; kept per account in tree-ranks.json, so a skill out of view keeps its last rank, and the item ranks off its tooltip in skill-ranks.json), and skills at the chosen step's rank lose their marks. The Skill tree tab's Edit points lets the player change the build's points (click adds, right-click removes; rules in `Deckard.Core/Builds/SkillPoints`: a node takes points when the tree reaches it from a hub, and keeps its last point while taken nodes hang from it); kept per account and build in skill-edits.json, they replace the guide's last step, so the build sheet and the in-game highlight follow them.
- Releases: `tools/installer/pack.ps1` publishes the app with the server's address built in (`DeckardServer` assembly metadata, read by `TradeClient`) and packs it with Velopack into `dist/` (git-ignored), signed with Azure Artifact Signing (`-AzureSignFile`, a metadata.json naming Synica's account and certificate profile, kept outside the repo; the signer is "CN=Synica, O=Synica, L=Breda, C=NL"). `Program.Main` runs Velopack's hooks before WinUI starts (`DISABLE_XAML_GENERATED_MAIN`); `Updater` checks the server's `/updates/` (from `Trade:UpdatesRoot`) after sign-in. `EnableMsixTooling` must stay on, or a published build has no compiled XAML and crashes at start.
- `src/Deckard.Cli`: `deckard capture` (capture and snapshots), `deckard affix "<line>"`, `deckard tooltip <png|folder>`, `deckard points <image>` (the skill tree's points spent and available).
- `src/Deckard.Core/Trade`: listing, realm (seasonal or eternal, softcore or hardcore) and search records shared by the app and the trade server.
- `src/Deckard.Trade.Api`: the trade server (ASP.NET Core minimal API, EF Core on PostgreSQL, hosted on Azure). Every endpoint needs a token issued after sign-in: Battle.net (`BattleNetLogin`: authorization code flow run by the server, which holds the client secret; users are keyed by Battle.net account id, so BattleTag renames keep their listings) or `/auth/dev-login` in development only, with per-player rate limits, requests capped at 256 KB (Kestrel; feedback and telemetry set their own), no CORS, and Development refusing to start on a database that isn't on this machine (`DevelopmentSchema.IsLocal`). Each sign-in is a row in `sessions` (`Sessions`): the token carries its id and works only while the row is there (checked per request, cached a minute), signing out (`DELETE /auth/session`) and deleting the account remove it, and rows the development sign-in made are refused outside development; a ban keeps the session, so a banned player can still export or delete their data. It can run as several instances: sign-ins and Patreon links in progress are in the database (`PendingSignIns`, each state or code taken once), and the background jobs, migrations and season rollover run under PostgreSQL advisory locks (`SingleInstance`); rate limits and the credits cache stay per instance (`docs/deploy-azure.md`, Scaling). `ListingRules` checks every listing against the season's `affix-templates.json` and works out which classes can use it (`itemTypeClasses`, class-specific powers and affixes). `DataEndpoints` serves the game data and icons to signed-in players from the data root (`Trade:DataRoot`, else the repo's `data/d4`), under their own rate limit. The schema is EF Core migrations (`src/Deckard.Trade.Api/Migrations`), applied when the server starts in every environment; change it with `dotnet tool run dotnet-ef migrations add <Name> --project src/Deckard.Trade.Api` (the tool is in `dotnet-tools.json`; run `dotnet tool restore` once) and commit the migration with the model change (`DevelopmentSchema` adopts development databases made before migrations). `dotnet run -- --reset --seed 500` fills the development database with dummy listings. `dotnet run -- --demo <BattleTag>` builds a market around one signed-in player (`DemoData`: their listings with offers, their offers in every state, deals with traders in game, buy orders, 30 days of sales). The app's Trade tab (`TradeView`, `TradeClient`) searches (collapsible filter panel; results in an `ItemsRepeater` with the virtualizing `MasonryLayout`), lists items and trades by offers: a buyer offers the asking price or less, and only an accepted offer (`OfferEndpoints`) shares the two BattleTags and reserves the listing. Search results never carry the seller's BattleTag. Open offers lapse with their listing: declined when it's sold or withdrawn, and, once it expired, when either side next looks (`OfferEndpoints.DeclineExpired`, from the Offers poll and My listings). Sellers can counter an offer (the buyer accepts or revises it); after a deal each side marks it completed or reports it, which makes up the trading records shown on offers. `/listings/price-check` gives asking and recently sold prices (the overlay card's Price check); `/listings/price-history` gives them per day over 30 days, drawn above search results by `PriceHistoryChart`. Buy orders (`WantedEndpoints`): a player posts a search and the gold they pay; selling an item that fits lists it and accepts the buyer's offer at once (the overlay card's Find buyers, the Trade tab's Buy orders page). Started on a new season's data, the server moves the old seasons' live listings and open buy orders to the eternal realm (`SeasonRollover`), as the game moves the items. `RetentionCleanup` deletes listings (with their offers and reports) and buy orders that ended over a year ago, once a day, as `docs/privacy-policy.md` promises. A player blocks another by right-clicking their listing, offer or buy order (`BlockEndpoints`, never revealing who): it works both ways, and Settings can only lift all blocks at once. Search can also leave out sellers with reports or without a proven record (`SellerTrust`). The item card's Queue gathers items read in game on My listings (`TradeView.Queue`), to price (Suggest prices) and list all at once. Abuse limits: 200 live listings per player, at most 3 identical ones, and `Moderation`: a player reported by 3+ partners with more reports than trades leaves the market until reviewed (off the market, banned or flagged, a player's listings and buy orders are hidden and they make no offers, deals or sales: `Moderation.AnyOffMarketAsync`) with `dotnet run -- --reports`, `--unflag <BattleTag>` or `--ban <BattleTag>`. Goods (runes, gems, elixirs, boss materials, from `AffixCatalog.Goods`) are listed by kind, name and quantity. `PresenceEndpoints`: the app reports with each poll whether the player is in game (shown only to others when they opt in) and, when location sharing is on, the zone, shown only to the accepted trade partner. The app polls offers every 15 s; `TradeToastWindow` shows new offers, counter-offers, acceptances, watched-search matches and expiring listings on the game's right edge while the game runs, otherwise they wait in the Offers page; `Deckard.Perception/Trade/TooltipListing` turns a read tooltip into a listing. `PatreonLink`: a signed-in player links Patreon (POST `/patreon/link` gives the authorize URL, Patreon calls back `/auth/patreon/callback`, which sends only `result=linked|already-linked|denied|failed` on to the app's loopback port; GET `/patreon` says linked and patron; DELETE `/patreon/link` unlinks), one Deckard account per Patreon account, kept in the `patrons` table; `/patreon/webhook` is the one endpoint without a player token: it acts only on a valid `X-Patreon-Signature` (HMAC-MD5 of the body) and only for `Trade:Patreon:CampaignId`. Patrons whose tier is in `Trade:Patreon:EarlyAccessTiers` get early builds from `/updates/early/` (the general `/updates/` never serves that folder), and patrons may be named in the credits (PUT `/patreon/credit`, GET `/supporters`; a moderator clears a name with `dotnet run -- --uncredit <BattleTag>`). Being a patron never touches the market (ROADMAP.md). `TelemetryEndpoints`: POST `/telemetry` keeps allowlisted usage events by install id, never an account or IP (raw 90 days, daily counts kept). `FeedbackEndpoints`: POST `/feedback` (multipart: kind, title, description, diagnostics, up to 3 screenshots, 5 a day) strips image metadata (`ImageSanitizer`), keeps screenshots in `Trade:FeedbackRoot` (never in the repo or on GitHub), and `GitHubIssues` files each report as a public issue in `Trade:GitHub:Repository` (the open-source repo; players are told it is public) that names no player (labels `bug`/`enhancement` + `from-app`; the project board's Auto-add workflow picks them up), retrying while GitHub is unset or down and deleting screenshots 90 days after the issue closes; `dotnet run -- --feedback <report>` copies a report's screenshots out, `--nofeedback <BattleTag>` stops a player sending. `AccountEndpoints`: GET `/account/export` (everything the server keeps about the player, as JSON) and DELETE `/account` (all of it; a banned or flagged account keeps only its id, BattleTag and the ban). Secrets (`ConnectionStrings:Trade`, `Trade:SigningKey`, `Trade:BattleNet:ClientId`, `Trade:BattleNet:ClientSecret`, `Trade:Patreon:ClientId`, `ClientSecret`, `CampaignId`, `WebhookSecret`, `EarlyAccessTiers`, `Trade:GitHub:Token`) live in user secrets or the host's settings, never in the repo.
- `tests/Deckard.Core.Tests`, `tests/Deckard.Perception.Tests`, `tests/Deckard.Trade.Tests`: xUnit tests. Trade API tests need a PostgreSQL connection string in `DECKARD_TRADE_TEST_DB` (that database is dropped and recreated) and are skipped without it. Perception tests use synthetic frames and recorded OCR text; game screenshots are never committed.

## Conventions

- Frames are tightly packed BGRA8 buffers rented from `ArrayPool`. Whoever reads a frame disposes it.
- `IFrameSource.Frames` keeps only the latest frame: slow consumers drop old frames instead of queuing them.
- `TreatWarningsAsErrors` is on. Run `dotnet build` and `dotnet test` before committing.
- D4 item data is seasonal. Never hard-code affix text, item names or stat lists in C#; read them from the season's `affix-templates.json`, and keep code working when a new season adds, removes or rewords entries.
- UI: dark only, in the palette of the item tooltips (`ItemCard`): near-black panels, warm gray text, the unique items' tan for titles and legendary orange as the accent, set in `App.xaml`. The main window is a left navigation rail (Items, Talisman, Mercenaries, Skill tree, Paragon, Stash, then a Trade group: Search, My listings, Offers, Buy orders, each a page of the one `TradeView`) under a build header. All text is PT Serif (the typeface of D4's own tooltips), SIL OFL, credited in `AboutDialog` and bundled in `src/Deckard.App/Assets/Fonts` with its license. Never bundle Diablo's own fonts (Exocet, the D4 tooltip font, or maxroll's copies of them): they are not free.
- `docs/`: `deploy-azure.md` (the trade server on Azure: `infra/azure/main.bicep`, `.github/workflows/deploy-trade-server.yml`), `moderation.md`, `github-feedback.md` (token and board setup), `terms-of-use.md` (published on synica.nl like the privacy policy; only the official app may use the trade service), and `privacy-policy.md`.
- `docs/privacy-policy.md` is Deckard's published privacy policy (Synica, hosted on Azure West Europe, 12 months' retention of finished trades). A change to what the app or the trade server keeps, shares or how long updates it in the same commit, with today's date as "Last updated"; then tell the user to republish it on synica.nl.
- `data/` is git-ignored third-party game data. Never commit it; tests use small inline fixtures instead.
- `affix-templates.json` carries a schema version that `AffixCatalog.SupportedSchemaVersion` must match, and a data revision checked against `AffixCatalog.ExpectedDataRevision` (older data still loads; the server logs a warning to produce it again). The private data tool changes with them.
- Line endings are LF in every file, enforced by `.gitattributes` (`* text=auto eol=lf`). Write files with LF, including from scripts (Python's text mode on Windows writes CRLF; pass `newline="\n"`). A diff that rewrites whole files is a line-ending change: fix it before committing.
- The repository is public under AGPL-3.0 (`LICENSE`), the trade server included. Never commit secrets, players' data, game screenshots or the live server's private details (keys, connection strings, subscription ids); the server must stay safe when anyone reads its code and sends it any request.
- Several Claude sessions work on this repository at once. Each works on its own branch, never directly on `master`.
- No pull requests, but every push to `master` needs the user's explicit approval, given for that push: ask, and until they say yes push only to your own branch. Once approved, fetch `origin/master`; if it moved, rebase the branch onto it and run `dotnet build` and `dotnet test` again. Then push the branch to `master` as a fast-forward (`git push origin HEAD:master`).
- `dotnet build src/Deckard.App` writes the app to `bin/Debug/<tfm>/win-x64/Deckard.exe`, a solution build to `bin/x64/Debug/<tfm>/win-x64/Deckard.exe`. Launch the one your build wrote, or you run a stale exe.
- Sessions also run the app at once. Record the PID of every process you launch and only stop, restart or reuse those, by PID; never kill by name or take over another session's window. If a build fails on a locked exe, report it instead of killing the holder.
